# 02. Requirements

> 업무 규칙의 단일 기준 문서이다. 다른 문서는 이 문서의 Requirement ID를 참조한다.

## 0. 용어

- 사용자 권한(role): `ADMIN`(관리자) / `EMPLOYEE`(일반 직원)
- 승인자: 휴가 신청 시 신청자가 지정한 사용자. 별도 권한이 아니며 본인을 제외한 모든 활성 사용자가 승인자가 될 수 있다.
- 승인 필요 여부(approval_required): 사용자별 휴가 승인 정책. `true`이면 승인자 승인 후 확정되고, `false`이면 신청 즉시 확정된다.
- 즉시 승인 건: 승인이 불필요한 사용자가 신청하여 `APPROVED` 상태로 생성된 휴가이다. 승인자(approver_id)가 없다.
- 기준 시간대: `Asia/Tokyo`

## 1. 기능 요구사항

### FR-AUTH-001: 로그인

- 사용자는 사원번호와 비밀번호로 로그인할 수 있다.
- 사원번호 또는 비밀번호가 잘못된 경우 로그인에 실패한다. 실패 사유(사원번호 오류와 비밀번호 오류)를 구분하여 안내하지 않는다.
- 비활성 계정은 로그인할 수 없다.
- 로그인 성공 시 인증 토큰과 인증된 사용자 정보(이름, 권한, 부서, 승인 필요 여부, 비밀번호 변경 필요 여부)를 반환한다.
- 비밀번호 변경이 필요한 사용자(최초 로그인)는 비밀번호를 변경하기 전에는 다른 기능을 사용할 수 없다.
- 비밀번호는 평문으로 저장하지 않는다.

### FR-AUTH-002: 로그아웃 및 인증 유지

- 인증은 JWT Access Token과 Refresh Token으로 처리한다.
- Access Token이 만료되면 Refresh Token으로 갱신한다. 갱신에 실패하면 로그인 화면으로 이동한다.
- Refresh Token의 유효 기간은 발급 후 7일이다.
- 갱신할 때마다 사용한 Refresh Token을 무효화하고 새 Refresh Token을 발급한다(회전).
- 로그아웃 시 Refresh Token을 무효화한다.

### FR-AUTH-003: 비밀번호 변경

- 로그인한 사용자는 현재 비밀번호를 확인한 뒤 새 비밀번호로 변경할 수 있다.
- 새 비밀번호는 현재 비밀번호와 같을 수 없다.
- 새 비밀번호는 8자 이상이며 영문과 숫자를 포함하고, 72바이트 이하여야 한다.
- 변경이 완료되면 비밀번호 변경 필요 상태를 해제한다.
- 변경이 완료되면 현재 세션을 제외한 해당 사용자의 다른 세션(Refresh Token)을 모두 무효화한다.

### FR-ATT-001: 출근 등록

- 로그인한 사용자는 본인의 출근을 등록할 수 있다.
- 출근 기록은 서버 시간을 기준으로 저장한다. 근무일(work_date)은 기준 시간대의 출근 날짜이다.
- 동일한 근무일에 출근 기록이 이미 존재하면 중복 등록을 방지한다.
- 이전 근무일에 퇴근하지 않은 기록이 있어도 당일 출근 등록은 가능하다. 그 기록은 `퇴근 누락` 상태로 표시된다.

### FR-ATT-002: 퇴근 등록

- 당일 출근 기록이 존재하는 경우에만 퇴근 등록이 가능하다.
- 퇴근 시간은 출근 시간보다 늦어야 한다.
- 퇴근 기록이 이미 존재하는 경우 중복 등록을 방지한다.
- 이전 근무일의 퇴근은 사용자가 직접 등록할 수 없으며 관리자가 수정한다(FR-ATT-005).

### FR-ATT-003: 개인 근태 이력 조회

- 로그인한 사용자는 본인의 근태 이력만 기간별로 조회할 수 있다.
- 근태 상태는 `근무 중`(당일, 퇴근 전), `퇴근 완료`, `퇴근 누락`(이전 근무일, 퇴근 없음)으로 구분한다.
- 조회 기간은 최대 1년(366일)이다. (잠정 기준, 확인 필요)

### FR-ATT-004: 전체 근태 조회 (관리자)

- ADMIN은 전체 사용자의 근태 기록을 사원, 부서, 기간, 상태별로 조회할 수 있다.
- 조회 기간은 최대 1년(366일)이다. (잠정 기준, 확인 필요)

### FR-ATT-005: 근태 수정 (관리자)

- ADMIN은 근태 기록의 출근 시간과 퇴근 시간을 수정할 수 있다.
- 수정 후에도 퇴근 시간은 출근 시간보다 늦어야 한다.
- 출근 시간은 해당 기록의 근무일(기준 시간대 날짜)을 벗어날 수 없다.
- 퇴근 시간은 다음 날이어도 되지만(자정을 넘긴 근무), 출근 시간으로부터 24시간 이내여야 한다.
- 수정 시 수정자와 수정 시간을 저장한다.

### FR-LEAVE-001: 휴가 신청

- 로그인한 사용자(ADMIN 포함)는 휴가 종류, 시작일, 종료일, 사유를 입력하여 휴가를 신청할 수 있다.
- 사유는 필수이며 최대 500자이다.
- 시작일은 종료일보다 늦을 수 없다.
- 시작일과 종료일은 같은 연도여야 한다. 연도를 걸치는 휴가는 연도별로 나누어 신청한다.
- 휴가 종류는 다음과 같다.

  | 코드 | 명칭 | 1일당 차감 일수 |
  |---|---|---|
  | ANNUAL | 연차 | 1 |
  | HALF_AM | 오전 반차 | 0.5 |
  | HALF_PM | 오후 반차 | 0.5 |
  | SPECIAL | 특별휴가 | 0 (차감 없음) |
  | OTHER | 기타 | 0 (차감 없음) |

- 반차(HALF_AM, HALF_PM)는 시작일과 종료일이 같아야 한다.
- 신청 일수는 시작일부터 종료일까지에서 토요일과 일요일을 뺀 일수이다(반차는 0.5일). 공휴일은 빼지 않는다.
- 신청 일수가 0일인 신청(기간 전체가 주말)은 할 수 없다.
- 날짜 중복: 본인의 `PENDING` 또는 `APPROVED` 휴가와 날짜가 겹치는 신청은 할 수 없다. 단, 같은 날의 HALF_AM과 HALF_PM은 서로 겹치지 않는 것으로 본다.
- 잔여 연차: 잔여 연차 = 해당 연도 부여 연차(FR-LEAVE-006) − 해당 연도 `APPROVED` 및 `PENDING` 상태 휴가의 차감 일수
  - 휴가의 연도는 휴가 시작일의 연도이다(신청일 기준이 아니다).
- 차감 대상 휴가(ANNUAL, HALF_AM, HALF_PM)는 신청 일수가 잔여 연차를 초과하면 신청할 수 없다. 즉시 승인 건도 동일하다.
- 승인 필요 여부에 따라 처리 방식을 구분한다.
  - 승인이 필요한 사용자: 승인자를 반드시 지정해야 하며, 신청은 `PENDING` 상태로 생성되고 지정한 승인자에게 승인 요청이 생성된다.
  - 승인이 불필요한 사용자: 승인자를 선택하지 않으며, 신청은 즉시 `APPROVED` 상태로 생성된다. 이때 승인자는 비워 두고 신청자를 처리자로, 신청 시각을 처리 시간으로 기록한다.
- 승인자는 본인을 제외한 활성 사용자 중에서만 선택할 수 있다.

### FR-LEAVE-002: 휴가 승인 및 반려

- `PENDING` 상태의 신청만 승인 또는 반려할 수 있다.
- 승인자는 본인에게 할당된 `PENDING` 휴가만 승인 또는 반려할 수 있다.
- ADMIN은 모든 `PENDING` 휴가를 대리로 승인 또는 반려할 수 있다. 이때 처리자는 승인자와 다를 수 있다.
- 신청자는 본인의 휴가를 승인 또는 반려할 수 없다(ADMIN 포함).
- 반려 시 반려 사유는 필수이며 최대 500자이다.
- 승인 또는 반려 처리 시 처리자와 처리 시간을 저장한다.
- 승인 시점에는 잔여 연차와 날짜 중복을 다시 검사하지 않는다(PENDING 단계에서 이미 반영되어 있음).
- 이미 처리된 신청(즉시 승인 건 포함)은 다시 처리할 수 없다.

### FR-LEAVE-003: 승인 대기 목록

- 승인자는 본인에게 할당된 `PENDING` 휴가만 조회할 수 있다.
- 다른 승인자에게 할당된 요청은 조회할 수 없다. 단, ADMIN은 모든 `PENDING` 휴가를 조회할 수 있다.
- 승인, 반려, 취소된 신청과 즉시 승인 건은 승인 대기 목록에 표시하지 않는다.

### FR-LEAVE-004: 휴가 취소

- 신청자는 다음 휴가를 취소할 수 있다.
  - `PENDING` 상태의 휴가
  - 즉시 승인 건 중 시작일이 오늘보다 뒤인 휴가 (시작일 > 오늘, 기준 시간대 Asia/Tokyo)
- 승인자 또는 ADMIN이 승인한 휴가와 반려된 휴가는 취소할 수 없다.
- 취소 시 상태를 `CANCELLED`로 변경하고 처리자(신청자)와 처리 시간을 저장한다. 물리 삭제는 하지 않는다.
- 신청 내용 수정 기능은 제공하지 않는다. 변경이 필요하면 취소 후 다시 신청한다.

### FR-LEAVE-005: 휴가 조회

- 사용자는 본인의 휴가 신청 이력을 조회할 수 있다.
- 휴가 상세는 신청자, 해당 휴가에 할당된 승인자, ADMIN만 조회할 수 있다.

### FR-LEAVE-006: 부여 연차 관리

- 부여 연차는 사용자별로 연도마다 관리한다.
- ADMIN은 사용자의 연도별 부여 연차 일수(0.5 단위)를 등록하거나 수정할 수 있다.
- 해당 연도의 부여 연차가 등록되지 않은 사용자의 부여 연차는 0일로 본다.
- 부여 연차는 해당 연도의 사용 일수(`APPROVED` 및 `PENDING` 상태 휴가의 차감 일수)보다 적게 수정할 수 없다.
- 잔여 연차는 저장하지 않고 조회할 때 계산한다.

### FR-USER-001: 사원 조회 및 등록 (관리자)

- ADMIN은 사원 목록을 이름, 사원번호, 부서, 권한, 승인 필요 여부, 계정 상태, 입사일 기간으로 검색할 수 있다.
- ADMIN은 이름, 사원번호, 초기 비밀번호, 입사일, 부서, 권한, 승인 필요 여부를 입력하여 사원을 등록할 수 있다.
- 입사일은 필수이며 기본값이 없다. 미래 날짜도 입력할 수 있다.
- 사원번호는 중복될 수 없다.
- 사원번호는 숫자(0~9)만 사용하며 최대 50자리이다. 앞자리 0은 그대로 유지한다(예: `00001`). 등록·수정·로그인 시 입력값의 앞뒤 공백을 제거한 뒤 검증한다.
- 로그인 시 사원번호가 숫자 형식이 아니면 사원번호 오류와 같이 처리한다(FR-AUTH-001, 실패 사유를 구분하지 않음).
- 신규 사원은 활성 상태로 등록되며, 최초 로그인 시 비밀번호를 변경해야 한다.

### FR-USER-002: 사원 정보 수정 (관리자)

- ADMIN은 사원의 이름, 사원번호, 입사일, 부서, 권한, 승인 필요 여부, 계정 상태, 부여 연차를 수정할 수 있다.
- 마지막 활성 ADMIN 계정은 비활성화하거나 EMPLOYEE로 변경할 수 없다.
- 계정을 비활성화하면 다음과 같이 처리한다.
  - 해당 사용자는 더 이상 로그인할 수 없고 승인자 후보에서 제외된다.
  - 해당 사용자가 신청한 `PENDING` 휴가는 `CANCELLED`로 변경한다. 처리자는 비활성화를 수행한 ADMIN, 처리 시간은 비활성화 시점이다.
  - 해당 사용자에게 할당된 다른 사용자의 `PENDING` 휴가는 그대로 유지하며 ADMIN이 대리 처리한다. 비활성화 전에 해당 건수를 경고로 안내한다.

### FR-DASH-001: 대시보드

- 모든 사용자에게 당일 근태 상태, 본인 휴가 현황(부여, 승인 완료, 승인 대기, 잔여), 본인에게 할당된 승인 대기 건(최대 5건)을 표시한다.
- ADMIN에게는 추가로 오늘의 전체 현황(출근 인원, 미출근 인원, 휴가 인원, 전체 승인 대기 건수)을 표시한다.
  - 휴가 인원: 오늘이 기간에 포함된 `APPROVED` 휴가가 있는 활성 사용자 수. 휴가 종류는 모두 포함하며, 반차 사용자도 센다(출근 인원과 중복될 수 있다).

## 2. 비기능 요구사항

### NFR-001: 보안
- 비밀번호는 안전한 해시 알고리즘(bcrypt 등)으로 저장한다.
- API 접근 권한을 서버 측에서 검증한다.
- 인증되지 않은 사용자는 보호된 API에 접근할 수 없다.
- Refresh Token은 httpOnly 쿠키로 전달한다.

### NFR-002: 성능
- 일반적인 목록 조회 API는 정상적인 데이터 규모에서 1초 이내 응답을 목표로 한다.
- 목록 조회는 페이지네이션을 지원한다(기본 20건).

### NFR-003: 유지보수성
- Controller, Service, Repository의 책임을 분리한다.
- DTO를 통한 입력값 검증을 수행한다.

### NFR-004: 동시성
- 휴가 신청 시 잔여 연차와 날짜 중복 검증은 트랜잭션 안에서 수행하여 동시 신청으로 인한 초과를 방지한다.
- 승인, 반려, 취소는 현재 상태를 조건으로 갱신하여 중복 처리를 방지한다.
- 부여 연차 수정은 같은 사용자의 휴가 신청과 동시에 실행되어도 사용 일수 미만이 되지 않도록 한다.
- 마지막 활성 ADMIN 검증은 동시 요청(두 ADMIN의 동시 비활성화 등)으로 위반되지 않도록 한다.
- 구현 방식은 05_DATABASE_DESIGN.md §8을 따른다.

## 3. 업무 규칙

- 출퇴근 등록은 사용자 본인의 기록만 할 수 있다.
- 근태 기록 수정은 ADMIN만 할 수 있다(FR-ATT-005).
- 관리자는 전체 사용자의 근태 정보를 조회할 수 있다.
- 신청된 휴가의 내용은 수정할 수 없다. 변경이 필요하면 취소(FR-LEAVE-004) 후 다시 신청한다.
- 승인 정책(승인 필요 여부)을 변경해도 이후 신규 신청에만 적용한다. 이미 생성된 휴가의 상태, 승인자, 처리 정보는 소급 변경하지 않는다.
