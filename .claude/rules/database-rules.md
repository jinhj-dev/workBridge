# Database Rules

## 1. 기본 원칙

- 데이터 무결성을 최우선으로 한다.
- 확정된 DB 설계 문서를 기준으로 구현한다.
- 정규화와 조회 성능의 균형을 고려한다.
- 중복 데이터 저장을 최소화한다.
- 확장성과 유지보수성을 고려한다.
- DB 구조를 임의로 변경하지 않는다.

## 2. 테이블 설계

- 하나의 테이블은 명확한 데이터 책임을 가진다.
- 테이블명은 기존 프로젝트의 명명 규칙을 따른다.
- 컬럼명은 의미를 명확하게 표현한다.
- 컬럼의 데이터 타입과 길이를 적절하게 설정한다.
- NULL 허용 여부를 명확하게 정의한다.
- 기본값은 업무 규칙에 근거하여 설정한다.
- 불필요한 컬럼을 생성하지 않는다.
- 동일한 의미의 데이터를 여러 테이블에 중복 저장하지 않는다.

## 3. 기본키 및 외래키

- 모든 주요 업무 테이블은 명확한 기본키를 가진다.
- 외래키는 테이블 간 참조 무결성을 유지하는 데 활용한다.
- 외래키의 삭제 및 수정 정책을 명확하게 정의한다.
- CASCADE 삭제는 업무 영향 범위를 확인한 후 적용한다.
- 식별자와 업무상 고유값을 구분한다.
- UNIQUE 제약조건을 활용하여 중복 데이터를 방지한다.

## 4. 인덱스 설계

- WHERE 조건에 자주 사용되는 컬럼을 검토한다.
- JOIN에 사용되는 컬럼의 인덱스를 검토한다.
- 정렬 및 검색 조건을 고려한다.
- 복합 인덱스는 컬럼 순서와 선택도를 고려한다.
- 중복되거나 사용되지 않는 인덱스를 남용하지 않는다.
- 인덱스 추가 시 INSERT, UPDATE, DELETE 성능에 미치는 영향을 고려한다.
- 인덱스는 실제 실행 계획을 통해 효과를 검증한다.

## 5. 조회 성능

- SELECT * 사용을 지양한다.
- 필요한 컬럼만 조회한다.
- 대량 데이터 조회에는 Pagination을 적용한다.
- N+1 조회 문제를 방지한다.
- 불필요한 JOIN을 최소화한다.
- 반복적으로 실행되는 동일 쿼리를 검토한다.
- 집계 연산이 많은 경우 별도 집계 구조의 필요성을 검토한다.
- 실행 계획(EXPLAIN 등)을 활용하여 병목을 분석한다.

## 6. 트랜잭션 및 동시성

- 여러 데이터 변경이 하나의 업무 단위인 경우 트랜잭션을 고려한다.
- 트랜잭션 범위는 필요한 최소한으로 유지한다.
- 긴 트랜잭션으로 인한 잠금 문제를 방지한다.
- 동시 수정 가능성이 있는 데이터는 적절한 잠금 전략을 적용한다.
- 낙관적 잠금과 비관적 잠금의 적합성을 검토한다.
- 중복 실행으로 인한 데이터 중복을 방지한다.
- 재시도 로직을 설계할 때 멱등성을 고려한다.
- 서로 다른 DB 또는 외부 시스템 간 데이터 일관성이 필요한 경우 별도의 보상 및 복구 전략을 검토한다.

## 7. 삭제 및 이력 관리

- 업무상 삭제와 물리적 삭제를 구분한다.
- Soft Delete 적용 여부는 업무 요구사항을 기준으로 결정한다.
- 삭제된 데이터의 조회 및 복구 정책을 정의한다.
- 변경 이력이 필요한 데이터는 이력 관리 방식을 정의한다.
- 개인정보 및 민감 정보의 보존 기간을 고려한다.
- 불필요한 이력 데이터가 무한히 증가하지 않도록 관리한다.

## 8. 공통 컬럼

다음 컬럼은 필요성에 따라 적용한다.

- created_at
- updated_at
- created_by
- updated_by
- deleted_at

모든 테이블에 무조건 적용하지 않는다.
업무 성격과 이력 관리 요구사항을 기준으로 결정한다.

## 9. Migration 규칙

- DB 구조 변경은 Migration으로 관리한다.
- 이미 공유되거나 운영 환경에 적용된 Migration을 임의로 수정하지 않는다.
- 기존 데이터를 유실시키는 변경은 사전 검토한다.
- Migration 실행 전후의 데이터 상태를 확인한다.
- 운영 DB에 직접적인 구조 변경을 수행하지 않는다.
- Rollback 또는 복구 방안을 고려한다.
- Migration 실행 순서와 의존성을 관리한다.

## 10. Seed 데이터

- 개발 및 테스트에 필요한 초기 데이터만 생성한다.
- 운영용 초기 데이터와 테스트 데이터를 구분한다.
- Seed 재실행 시 중복 데이터가 발생하지 않도록 한다.
- 실제 개인정보를 테스트 데이터로 사용하지 않는다.
- 비밀번호 등 인증 정보는 안전하게 처리한다.

## 11. 데이터 보안

- DB 접속 정보를 코드에 하드코딩하지 않는다.
- 최소 권한 원칙을 적용한다.
- 개인정보 접근을 제한한다.
- 민감 정보는 필요한 경우 암호화한다.
- 로그에 개인정보나 인증 정보를 출력하지 않는다.
- SQL Injection 방지를 위해 ORM 또는 파라미터 바인딩을 활용한다.

## 12. DB 변경 승인 규칙

다음 변경은 반드시 사용자 승인 후 진행한다.

- 확정된 테이블 구조 변경
- 컬럼 삭제
- 컬럼 타입 변경
- PK 및 FK 변경
- 기존 데이터에 영향을 주는 Migration
- 삭제 정책 변경
- 데이터 정규화 구조 변경

## 13. 완료 기준

- 설계서와 실제 DB 구조가 일치하는가?
- PK / FK가 적절하게 설정되었는가?
- 제약조건이 업무 규칙을 반영하는가?
- 인덱스가 적절한가?
- 동시성 문제가 없는가?
- Migration이 정상 실행되는가?
- 데이터 유실 위험이 없는가?
- 필요한 테스트가 통과하는가?
