# Coding Standards

## 1. 기본 개발 원칙

모든 코드는 다음 원칙을 준수한다.

- 가독성을 최우선으로 한다.
- 단순하고 명확한 코드를 작성한다.
- 단일 책임 원칙(SRP)을 준수한다.
- 중복 코드를 최소화한다.
- 유지보수성과 확장성을 고려한다.
- 불필요한 추상화와 과도한 설계를 피한다.
- 기존 프로젝트의 아키텍처와 코딩 패턴을 우선적으로 따른다.

## 2. TypeScript 규칙

- 가능한 한 TypeScript의 엄격한 타입 검사를 활용한다.
- any 사용을 원칙적으로 금지한다.
- 불가피하게 any를 사용해야 한다면 사유를 명시한다.
- unknown을 적절히 활용하여 타입 안정성을 확보한다.
- 명시적인 반환 타입을 작성한다.
- 타입 단언(as)은 필요한 경우에만 사용한다.
- Non-null assertion(!)을 남용하지 않는다.
- 중복 타입 정의를 방지한다.
- 공통 타입은 적절한 위치에서 재사용한다.

## 3. 네이밍 규칙

### 변수 및 함수
- camelCase 사용
- 의미를 명확하게 표현
- 축약어 및 의미 없는 이름 사용 금지

예시:
- getUserById
- calculateTotalAmount
- isApprovalCompleted

### 클래스 및 컴포넌트
- PascalCase 사용

예시:
- UserService
- ApprovalController
- LoginForm

### 상수
- UPPER_SNAKE_CASE 사용

예시:
- MAX_RETRY_COUNT
- DEFAULT_PAGE_SIZE

### 파일명
- 기존 프로젝트의 파일명 규칙을 우선한다.
- React 컴포넌트는 PascalCase를 권장한다.
- 유틸리티 및 일반 TypeScript 파일은 기존 프로젝트 컨벤션을 따른다.

## 4. 함수 설계

- 하나의 함수는 하나의 명확한 책임을 가진다.
- 함수가 지나치게 길어지면 의미 있는 단위로 분리한다.
- 중첩 조건문을 최소화한다.
- 불필요한 함수 분리를 피한다.
- 함수 이름만으로 역할을 이해할 수 있어야 한다.
- 부수 효과가 있는 함수는 명확히 구분한다.
- 매개변수가 지나치게 많아지면 객체 형태로 전달하는 것을 고려한다.

## 5. 아키텍처 및 책임 분리

### Backend
- Controller는 HTTP 요청과 응답을 처리한다.
- Service는 비즈니스 로직을 담당한다.
- Repository 또는 데이터 접근 계층은 DB 접근을 담당한다.
- DTO는 요청 및 응답 데이터 구조를 정의한다.
- Entity는 데이터베이스 구조를 표현한다.
- Controller에 복잡한 비즈니스 로직을 작성하지 않는다.
- Service에 직접적인 HTTP 요청 객체 의존성을 남용하지 않는다.

### Frontend
- Page는 화면 단위의 조합과 라우팅을 담당한다.
- Component는 재사용 가능한 UI를 담당한다.
- Custom Hook은 재사용 가능한 상태 및 로직을 담당한다.
- API 호출 로직과 화면 표현 로직을 적절히 분리한다.
- 서버 상태와 클라이언트 UI 상태를 구분한다.
- 컴포넌트에 지나치게 많은 책임을 부여하지 않는다.

## 6. 에러 처리

- 예외를 무시하는 코드를 작성하지 않는다.
- 빈 catch 블록을 금지한다.
- 오류의 원인을 추적할 수 있도록 처리한다.
- 사용자에게 내부 시스템 오류나 민감한 정보를 노출하지 않는다.
- 예상 가능한 비즈니스 오류와 시스템 오류를 구분한다.
- 동일한 오류를 여러 계층에서 중복 처리하지 않는다.

## 7. 성능 최적화

- 불필요한 렌더링을 방지한다.
- 불필요한 DB 조회를 방지한다.
- N+1 쿼리 문제를 주의한다.
- 대량 데이터는 Pagination을 적용한다.
- 불필요한 메모리 복사를 최소화한다.
- 캐싱은 데이터 일관성과 무효화 전략을 고려하여 적용한다.
- 성능 최적화는 실제 병목을 확인한 후 수행한다.

## 8. 보안

- 인증과 인가를 구분한다.
- 사용자 입력값을 신뢰하지 않는다.
- SQL Injection을 방지한다.
- 민감한 정보를 로그에 출력하지 않는다.
- 비밀번호 및 인증 정보를 코드에 하드코딩하지 않는다.
- 환경변수를 활용하여 비밀 정보를 관리한다.
- 권한 검증은 서버 측에서 수행한다.

## 9. 코드 수정 규칙

- 기존 구현을 먼저 분석한다.
- 기존 구조를 무시하고 새로운 구조를 임의로 도입하지 않는다.
- 요청하지 않은 기능을 추가하지 않는다.
- 관련 없는 파일을 수정하지 않는다.
- 공통 컴포넌트나 유틸리티를 수정할 때 영향 범위를 확인한다.
- 설계 변경이 필요한 경우 사용자 승인을 요청한다.

## 10. 완료 기준

작업 완료 전 다음 항목을 확인한다.

- 코드가 기존 아키텍처와 일치하는가?
- 불필요한 중복 코드가 없는가?
- 타입 안정성이 확보되었는가?
- 예외 처리가 적절한가?
- 보안 문제가 없는가?
- 관련 테스트가 통과하는가?
- 불필요한 파일 수정이 없는가?
